## 3. 真正的设计冲突与处置

### 3.1 时间权威：三条日推进路径、两个日历对象（本轮核验修正最多的一条）

**冲突（已验证）**
- MAIN：`GameManager.advance_days(n)` 是自述「全局唯一的日推进入口」（`GameManager.gd:59`），每日固定顺序 `Calendar.advance_days(1)` → 跨月时 `GameState.accrue_interest()`、`Crew.pay_wages()`、`monthly_notice.emit` → `Economy.on_day_passed()` → `Fleet.on_day_passed()`（`:61-71`）。全仓 `Calendar.advance_days` 只此一处调用。
- CODEX 路径二：`WorldWeatherTime._process` 的 while 体（`:38-62`）先 `GameState.advance_world_day()`、再 `GameState.process_daily_consumption()`（`:41-42`），后者末尾 `calendar.advance_days(1)`（`GameState.gd:242-243`）；同一 while 体还接着调 `WorldEventTracker.process_day()`、`TradeEventGenerator.try_generate()/process_day()` 等 5 个日结项，以及依赖 `_map/_ship` 的浮字 UI。
- CODEX 路径三：`GameState.rest_to_next_month()` 循环调 `process_daily_consumption()`（`:245-251`）。
- **两个日历不是同一个对象**：MAIN `Calendar` 是 autoload Node；CODEX `calendar` 是 `GameState` 持有的 `CalendarState` RefCounted（`GameState.gd:23/35`）。综合稿初版说「追加会让同一日历推两次」不准确，真实后果是**双日历漂移 + 存档双写**；若把 CODEX 的 calendar 指到 MAIN autoload 又在 `Calendar.advance_days` 里追加，则是无重入保护的无限递归（`Calendar.gd:33`）。
- 水粮双扣的真因是 MAIN `Fleet.on_day_passed` 已扣水粮（`Fleet.gd:442-444`）与 CODEX `SurvivalState.process_daily_consumption`（`:42-47`）重叠，与日历无关。
- **`TimeSystem` 在两棵树里都不存在**（grep 零命中，已验证）。它是本方案新造的抽象，不是移植。

**推荐处置**
1. **只留一个日历对象**。推荐保留 CODEX `CalendarState`（已进存档、有 256 行断言锁行为），把 MAIN `Calendar` 的三块内容搬进去：季风表（月份→东北/西南/转换，强度 1.0/0.8/0.3，bearing 225°/45°）、南宋 6 段年号表、中文日期串。MAIN `Calendar` autoload 退役。注意 `Main.gd:948-973` 的候风预报把季风表**重复手写了一遍**（读者材料），收敛时一并删。→ 待确认（设计判断，列入第 6 节）
2. **新建 `TimeSystem`（autoload）作为唯一日闸**，实现体照抄 MAIN `advance_days` 的顺序，尾部追加 CODEX while 体里的 5 个日结项，末尾 `emit day_advanced`。
3. **`WorldWeatherTime` while 体只保留** `time_of_day` 累加、`paused` 闸和一次 `TimeSystem.advance_days(1)`；浮字 UI 改为监听 `day_advanced` 留在原节点。不能「把 while 体追加到 advance_days 尾部」，也不能只写一行 `advance_days(1)` 把 5 个日结项静默丢掉。
4. `rest_to_next_month()` 循环体改调 `TimeSystem.advance_days(1)`。
5. `GameState.process_daily_consumption()` 里的 `calendar.advance_days(1)` **删除**，推日只在 TimeSystem 一处。代价：`TestRunnerCalendar.gd:90-93` 那两条「process_daily_consumption 同步推进日历」的断言（已验证存在）要改写成对 TimeSystem 的断言，列入扔掉清单。
6. **水粮日耗只留一份实现**：`SurvivalState` 保留为状态容器（存档与 UI 读它），逻辑按 MAIN `Fleet.gd:435-445` 重写（`at_sea` 在港豁免、整数份、占舱），MAIN `Fleet.on_day_passed` 的水粮段删除。
7. 为「一日只推一次日历」写不变量断言（`calendar_day_delta == 1`），不写死日期。

**丢什么**：CODEX 各系统自行决定结算时机的自由度；MAIN `Calendar` 文件本体；两条现有断言。

### 3.2 航海：两层共存，不是二选一（核验修正：AppRoot 必须改）

**冲突**：MAIN `SeaChart.gd` 是逐日推进的战略海图；CODEX `WorldMap` 是实时操船的战术层。

**推荐处置**：**都留**。`AppRoot` 增加 `show_seachart()`，新增 `MODE_SEACHART` 作远洋战略层，`WorldMap` 作沿岸/入港战术层。切换点推荐放在离/靠港：`SeaChart._arrive()`（`:677`，已验证）与 CODEX 的入港路由。

**「零风险」范围要修正（已验证）**：
- 成立的部分：`ModeStack._is_host()` 只检查 `has_method("show_voyage") and has_method("show_narrative")`（`ModeStack.gd:36-37`），`go_voyage/go_narrative` 只做 find_host + call，不枚举模式常量。所以宿主识别、这两个函数、全部 Controller 调用方都不用改。
- **必须改的部分：宿主 `AppRoot` 本身**。`show_voyage/show_narrative` 只 `queue_free` `_voyage`（`AppRoot.gd:99-101`、`:110-112`），`show_combat` 与两个 `_restore_after_*` 也只暂停/恢复 `_voyage`（`:151-152`、`:189-190`、`:400-401`）。新增的 seachart 节点既不会被拆除也不会被暂停恢复，五处都要加对应分支。
- `go_seachart` 必须照 `start_combat/play_cutscene` 的 `has_method` 守卫范式写（`ModeStack.gd:66-68`、`:82-84`，读者材料），否则会打到 `TestRunner.gd:2565` 那个只有 `show_voyage/show_narrative` 的 stub 上（已验证 stub 存在）。

**丢什么**：不丢代码，丢「一个航海玩法」的干净感，玩家要理解两种航行状态的切换。

### 3.3 战斗：一套系统，两个入口

**冲突**：MAIN 实时炮战（`Ship.gd` + `Cannonball.gd` + `PirateShip.gd`，经 `GameManager.pending_battle` 信箱与 `battle_finished` 信号挂上 SeaChart；读者材料）；CODEX 回合制 `CombatState`（Phase/Tactic/DUEL 全套）。

**推荐处置**：**只留 CODEX `CombatState`**，战略层遭遇与战术层遭遇都路由到它。MAIN 的 `Cannonball.gd` / `PirateShip.gd` / MAIN 侧 `Ship.gd` 开火与碰撞链整体退役。理由：两个方案（A、C 初稿）都试过「保留 Cannonball 改 group 判定」，两位评审都指出 CODEX 没有实时炮弹场景，保下来的 Cannonball 与 PirateShip 没有消费者，是孤儿代码。

**丢什么**：MAIN 侧的实时手感与接舷夺船体验。这是本方案最大的一笔丢弃，单列第 6 节第 1 题。

### 3.4 `class_name Ship` 的三方归属

**冲突**：`class_name Ship` 只在 MAIN `Ship.gd:1` 注册，唯一消费点是 `Cannonball.gd:27` 的 `body is Ship`，下一行 `:28` 调 `Fleet.armor_damage_reduction()`；CODEX `Ship.gd:34-35` 的 `add_to_group("player_ship")` 有 7 个消费点；`TestRunnerCrateLimits.gd:64-68` 直接断言 CODEX `Ship.gd` 源码文本（读者材料）。

**推荐处置**：3.3 退役 `Cannonball.gd` 后争夺自动消失，**路径 `scripts/Ship.gd` 归 CODEX 版本**，group 判定、7 个消费点、源码断言原样存活。需同步：`scenes/Ship.tscn` 的 `ext_resource` 指向、`TestRunnerCrateLimits.gd:60` 的路径断言。

### 3.5 补给/货舱：四条独立冲突轴（已验证）

| 轴 | MAIN | CODEX | 推荐 |
|---|---|---|---|
| 补给是否占舱 | 占：`used_capacity()` 首行 `float(water + food) * SUPPLY_BULK`（`Fleet.gd:126-131`） | 不占 | **取 MAIN**（否则远洋补给不构成取舍） |
| 舱容来源 | Σ 每船 capacity | 全局 `MAX_CARGO := 200`（`SurvivalState.gd:10`） | **取 MAIN**（多船编队才有意义） |
| 在港豁免 | 有：`if not at_sea:` 只回士气 + 腐损后 return，水粮不动（`Fleet.gd:435-441`；注释「泊港期间水手上岸」） | 无条件扣 | **取 MAIN** |
| 断粮惩罚 | 概率 0.4 × Crew 修正，损 3%，士气 −6（读者材料） | 确定性 10%（`STARVATION_DEATH_RATIO := 0.1`，`:12`） | **取 MAIN**（确定性 10% 会瞬间雪崩） |

**量纲换算是硬约束**：MAIN `CREW_DAYS_PER_SUPPLY := 2.0`（`:45`），1 份 = 2 人日，整数；CODEX `DAILY_CONSUME_DIVISOR := 10.0`（`:11`），1 点 = 10 人日，浮点。**换算系数 5**。CODEX 存档里的 `food/water` 需 ×5 转成份并收敛为 int。算式复核：60 人 `daily_supply_use()` = ceil(60/2.0) = 30，水、粮各扣 30（`:443-444`），一日实耗 60 单位 × 0.25 = **15.0 料占舱**（不是 7.5，那是把 30 当成水粮合计的错法）。

**丢什么**：CODEX 三个常量及所有直接读 `GameState.food` 浮点值的 UI 与断言。

### 3.6 `pu_attention` 量纲：静默回归风险最高的一条（核验修正：方向反了）

**冲突（已验证）**：CODEX 三处硬钳 `clampi(v, 0, 20)`（`GameState.gd:158`、`:433`、`:610`），阈值 `CUSTOMS_BLOCKED_ATTENTION := 15`（`state/TradeState.gd:7`）。MAIN 裸变量无上界（`GameState.gd:20`），步进 `+30`（`:256`）、`+8`（`:260`）、`+20 + contraband*2`（`:280`），阈值 `> 50`（`:266`），UI 档位 70/50/25（`Main.gd:589-595`），赎买 `-15`（`Main.gd:1058`）。

**危险点**：把 MAIN 86 行市舶司逻辑原样搬进 CODEX，`+30` 被钳成 20，`> 50` 分支永远不成立，走私查缉整条支线静默失效，两边现有断言都抓不到。

**推荐处置（按核验修正）**
- **量纲基准只能选 0–20**。综合稿初版写「要改 `SceneVariantResolver` 6 处阈值」方向反了：`SceneVariantResolver`、`PortStatusBar.gd:211-226`、`FactionSystem.gd:23`、`ConditionEvaluator` 的 `pu_attention_min` 都是 CODEX 自己的，本就按 0–20 标定，**不改**。更硬的理由：CODEX 13 个 JSON 里有 90 处按 0–20 标定的 pu_attention 增减值，MAIN 侧 JSON 为 0 处（已验证）。
- **要改的是 MAIN 的 7 个字面量**：`GameState.gd:256/260/266/280` 与 `Main.gd:589-595/1058`，按 ×0.2 折算（+30→+6，+8→+2，+20→+4，>50→>10，70/50/25→14/10/5，−15→−3）。
- **第二处静默失效**：MAIN 风险公式 `0.25 + float(pu_attention) / 400.0`（`GameState.gd:247`）在 0–20 下最多加 0.05，退化为近似常数，要同步改分母（例如 /80）。→ 数值待确认
- **存档口子**：`TradeState.from_dict` 只有下界 `maxi(0, …)`（`:19`），`GameState.from_dict` 直调 `trade.from_dict`（`:906`）；越界值会绕过三处 clamp 落地，让贿赂永久被拒、官军永久敌对。MAIN 目前没有需要迁移的存档，但 `from_dict` 仍应补上界，这是一行的事。
- 折算后必须为「走私被查缉」分支**新写一条专门断言**。

### 3.7 两个 `GameState.gd`：同名同义但量纲不兼容

**冲突**：五个顶层字段撞名：`pu_attention` / `has_customs_permit` / `fame` / `flags` / `last_port`。CODEX 把状态拆成 10 个 `state/*.gd`，顶层用属性代理（如 `GameState.gd:156-158`）；**最深的耦合是钱**：CODEX 顶层没有 money 字段，所有金钱变动走 `LedgerSystem`（读者材料）。

**推荐处置**：CODEX `GameState` + `state/*` 结构保留为骨架；MAIN `GameState` 只贡献市舶司（`:205-297`，86 行）与章节晋升（`:126-193`，68 行）两块，移植成 `state/` 下新模块或并入 `TradeState`/`CareerState`。移植市舶司前先补齐 4 个前置依赖：`Fleet.cargo/clear_cargo/remove_cargo/cargo_qty` → `CargoSystem`；`Economy.tariff_rate`；`GameManager.chapters_data`；`get_good_by_id/get_port_name`。
