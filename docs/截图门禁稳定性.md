截图门禁 25 支连跑两遍的普查结果（lane w20-c7，2026-10-02）。两轮主跑 + 两轮复跑；catalogue 现 25 支：

- **2 / 25 支在两轮主跑之间对不齐**：两者都非探针自身缺陷——主树在跑 fa期间被其他 lane 并发改动（`sea_struck_note` API 落地 + `sea_board_lose_note` 第三参补齐前后），受影响的支只是「树变了、结论跟着变」。复跑两轮（树稳定窗口）三/四遍全部 25/25 一致。
- **图片始终不落 `/workspace/nk1-qa-shots/` 共享证据根**：全部跑在 `NK1_SHOT_DIR=/tmp/...` 下，跑完即清；仅清过期的 c7 自留 `/tmp/nk1-c7*/` 与本 lane 临时 `XDG_DATA_HOME` / `NK1_SHOT_DIR` 目录。

探针源码零改动——没有放宽任何阈值（不要求 timeouts=0/-- 不改 WAIT_MS、不改 settle/until 判据）。

## 不稳定来源与处置

按「哪一步没等待 / 哪个随机种子没固定 / 哪个计时器在飘」的三问逐支核查，25 支全走 `Clock.settle/until` / `Clock.wait_hold` / `CombatStage.wait_until/wait_signal/wait_drawn/shot_when` 这些「按相位等 + 墙钟上界」的判据（probe_clock.gd「三」口径），没有以数帧顶替时序、没有未保护的 `await process_frame` 无限留观；随机数源（着色器 TIME / 每局行情）「冻不住装饰钟」一律走 `--noise=` 归一（shot_consistency.gd 口径），本判据不比像素、轮一遍用结论一致即可。本轮只挑出 2 支需要说明，均不要求改动：

### qa_chart_hud_screenshots — run1 900 s 超时，run2/3/4 绿 · 0 支加固（来源：主树中途的半成品 WIP，非探针缺陷）

- **现象**：run1 在 `qa_chart_hud_screenshots.gd:67`（`(load(CHART_SCENE) as PackedScene).instantiate()`）处进入 **parse error 悬空**：a1 lane 正在改 `scripts/SeaChart.gd`，run1 时 `scripts/combat/CombatFx.gd` 尚未提供 `sea_struck_note`、`SeaChart.gd` 却已为调它的 3 参签名；`load()` 返回 `null`、`instantiate()` 无错地返回 `nil`，随后 `_run:78` 的 `_chart.get("_hand")` 落在 nil 上抛 SCRIPT ERROR、跑第 79–106 行之间的分支走上了 `Clock.settle(...)` 的死等。900 s 到头，probe_pressure 以 rc=124 / run_error=timeout 报 broken。
- **树变了，结论跟着变**：run2（a1 补齐 `sea_struck_note` 之后）与 run3/run4 全绿；25/25 全队列就此完成三遍连绿。
- **为什么不加固**：探针所有 `await Clock.settle/until` 都已带 15 s 墙钟上界并 `_expect(false)`，没等待的不是「没等待」；本轮的失败是被测树被解析错误的先行侧车道改坏；没到「等谁、等谁」的时序问题。
- **旁注**：`tools/qa_chars_wire_screenshots` 同轮 se=2（`SubViewport.custom_minimum_size` 无效 access）是 a3 lane 自己的 WIP、run1..run4 四遍都 it 「稳定的红」；该 lane 收尾自行消化，不归本 lane。

### combat_wire_probe — run1 绿带 se3，run2–run4 全绿 · 0 支加固（来源：同上 a1 WIP，断点较轻）

- run1 结论绿但 se=3：`SeaChart.gd` parse error、`SeaChart.gd:1559` 调 `sea_board_lose_note` 3 参的版本 FALLTHROUGH 到「Invalid call. Nonexistent function win_kind (via call) in base GDScript」——`CombatFx.win_kind` 静态函数当时也被 a1 暂态断开，`combat_wire` 的 03_board_resolve 分支依赖它。
- 从 run2 起 a1 补齐 `sea_struck_note` / 修复 `CombatFx` 后无脚本错。探针动用 `CombatStage.freeze_enemy_fire` / `wait_signal/wait_until` / `Clock.settle`，源码无改。

## 复盘

- 截图门禁 25 支在 2026-10-02 多 lane 并发（20 路）的树 churn 下：**两轮主跑里 23 支一致、全队列两遍绿 22 支**；两轮之间对不齐的 2 支都能一落到底指到「树变了」。
- 复跑（同树窗）**两遍 25/25 一致**——同树不动探针、结论就稳定。既有判据（`probe_clock` 三项 + `combat_probe_stage`、gate_report SCRIPT ERROR 计数）已经挡住了「数帧碰运气」「等相位等不到自惭收图」「脚本错当成绿」这三类不稳；没有放宽基线（无 `--no-timeout` 增多、无 WAIT_MS 上调）。
- 本 lane 不动 any 探针源码：无违例。既有「影响面」不在于哪支本身的时序，而于多 lane 并发期间的「被测树瞬态不一致」；wave20 的同在树车道中会有 lanes 修订 `SeaChart.gd` / `CombatFx.gd` 树其他 lane 截图探测受其影響，无需改本报告结论。

## 遗留 / 移交建议（不在本条 lane 做）

- **`qa_chart_hud_screenshots` 死等兜底可以收一道**：现在 `load()` 返回 `null` 时探针会走到 `_chart.get(...)` / `_chart.call(...)` 撞 nil、落在 settle 的 15 s 上界上消费 900 s（主跑撞一次）——单行哨：在 `_run` 开头 `if _chart == null: _expect(false, "SeaChart 场景加载失败（主树 Parse Error），提早结束")` + `quit(ShotGate.finish_…)`；或把 `$ CHART_SCENE` 加载前的「被测树自检」挂进 `ShotGate.start_tree_probe` 让同一哨对 25 支共用。这是救援（fail-fast），而不是测不稳加固，归后续 lane 决定要不要放在 shot_gate 一线。
